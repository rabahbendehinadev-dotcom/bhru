## B. Actual request construction

- URL: supplied `https://api.ifreeicloud.co.uk`, normalized to the equivalent
  `https://api.ifreeicloud.co.uk/`. No API suffix, query credentials or redirects.
- HTTP method: POST.
- Content-Type: `application/x-www-form-urlencoded`.
- Form fields: `username=[REDACTED]`, `apiaccesskey=[REDACTED]`,
  `action=accountinfo`.
- Headers: `Accept: application/json`, `Accept-Encoding: identity`; no Bearer.
- **No `requestformat` field.** No `parameters` field for accountinfo.
- TLS certificate validation remains enabled. DNS answers must all be public;
  the actual connection uses a vetted pinned address. DNS/response deadlines are
  5/20 seconds; response limit is 8 MiB.

### Newly inspected official client evidence

DHRU's [official API Integration help article](https://help.dhru.com/en/articles/10892898-api-integration)
links a [PHP client archive](https://downloads.dhru.com/io/afaebd49-abef-4a83-8e6b-7a0ba338ea30/8fb6bc21-1d1c-4d74-952f-a4351eea9773_api.zip).
Downloaded into `/tmp` and inspected, without executing PHP:

- `api/dhrufusionapi.class.php`
- `api/get_account_info.php`
- `api/header.php`
- `api/README.txt`

That client sends `requestformat=REQUESTFORMAT`; its account example defines
`REQUESTFORMAT` as `"JSON"` and calls `accountinfo`.
**BHRU's omission is a confirmed difference from this official client.**
The Accept header is not equivalent to an application-level form selector.

Important qualification: the client identifies itself as **API kit 2.0, 2012**,
although linked from the current official help article. Its other conventions
include multipart POST, XML parameters, generic `/api/index.php` suffix and
disabled TLS verification. Do not copy these blindly into the v6.1 adapter.
This is not proof that iFree requires requestformat or defaults to XML.

The attached official v6.1 listener was also inspected:
`dhru-fusion-api-standards-master/README.md` and `api/index.php` inside
`attached_assets/dhru-fusion-api-standards-master_1791591349028.zip`.
It reads POST username/apiaccesskey/action, implements accountinfo, emits JSON
with `Content-Type: application/json; charset=utf-8`, and does not require
requestformat. Its optional parameters are Base64 JSON, unlike the older kit.
These references explain why the existing canonical mock passes despite the
client difference; neither reference proves real iFree behavior.

## C. Conditions producing INVALID_RESPONSE

| Layer | Conditions |
|---|---|
| Transport / input | Invalid serialized credential shape or forbidden action; HTTP non-2xx other than 401/402/403/429/5xx, including redirects and HTTP 400 |
| Transport / format | Missing/non-JSON Content-Type; XML/HTML/text MIME, even when body is JSON; non-identity Content-Encoding; response exceeding 8 MiB |
| Shared parser | Invalid JSON, BOM/other unhandled JSON prefix; non-object root; unsupported value types, lengths/control characters; non-uppercase three-letter currency; unsupported decimal/money representation |
| Legacy envelope | Malformed/empty ERROR; any provider ERROR other than exact `Authentication Failed`; optional apiversion not exactly `6.1`; SUCCESS not exactly one object; unsupported root paging markers |
| Account | Missing/non-object `SUCCESS[0].AccoutInfo` (the documented spelling); invalid present credit/currency |
| Catalog only | Missing account currency; malformed LIST/groups/SERVICES; excessive counts; invalid/mismatching/duplicate service IDs; invalid names/cost/metadata values |
| Saved worker only | Configured/upstream currency disagreement; non-ProviderError exceptions other than credential 503, including internal failures, are also collapsed into INVALID_RESPONSE |

Unsupported catalog requirement types ordinarily become review reasons, not
connection-test failures. They cannot explain an accountinfo-only draft test.

Other categories must not be conflated:

- DNS, TCP/TLS failures, timeout, aborted response, HTTP 429/5xx → `UNREACHABLE`.
- HTTP 401/402/403 → Legacy `AUTHENTICATION_FAILED`.
- JSON ERROR with exactly `MESSAGE: "Authentication Failed"` → same category.
- Differently worded authentication/IP restriction/disabled-account errors
  returned as HTTP 200 JSON → **INVALID_RESPONSE** under current classification.
- Draft configured-currency disagreement → HTTP 409, not the supplied category.

**Diagnostic information is lost:** `ProviderError` retains only category and
retryability, not safe parsing stage, HTTP status/MIME or vetted error code.
The route returns only the category; the UI adds generic advice. It cannot
distinguish format failure from IP Guard or another provider error.

Confirmed parser limitations include rejection of non-JSON responses, JSON with
non-JSON MIME, and error wording variants. No captured iFree response establishes
that any rejected variant is a valid **iFree v6.1 success**. Do not claim that
the actual provider response was incorrectly rejected without evidence.

## D. iFree compatibility and remaining questions

Fetched the unauthenticated official [iFree API Setup page](https://api.ifreeicloud.co.uk/setup/setup).
It confirms “Dhru API v6.1”, separate Dhru and PHP integrations, copying supplied
configuration, Verify Connection and synchronization. Its publicly accessible
text does **not** document accountinfo wire fields, requestformat defaults,
response schema/MIME, error codes or IP Guard first-connection rules.

Confirmed from the v6.1 DHRU reference: POST credentials/action, accountinfo,
SUCCESS/AccoutInfo/credit/currency and Authentication Failed envelope. Confirmed
from user-supplied provider details: supplied root URL, Dhru enabled, USD,
IP Guard enabled and previously pending linked IP.

Unresolved: iFree's required format selector and default representation; exact
account response/error envelope and headers; independent verification of the
account-specific URL/path; whether this failed request was blocked by IP Guard.
No public documentation found in this investigation establishes these details.

The separate PHP API uses a different contract. Its documentation/client is
**not evidence for DHRU requests** and was not used as an implementation basis.
No `/api.php` or `/api/index.php` fix is justified for iFree from these sources.

## E. Root cause assessment

- **Confirmed:** BHRU omits the JSON selector present in the official historical
  client, accepts only JSON MIME/body, and hides failure reasons behind a category.
- **Strongly supported candidate, not proven iFree root cause:** missing
  `requestformat=JSON` could lead to a different default response representation
  and the observed INVALID_RESPONSE. An offline conditional fixture reproduces
  exactly this failure; the fixture is not a recording of iFree.
- **Unverified alternatives:** HTTP-200 IP Guard/auth/permission error with
  different wording; incorrect endpoint behavior/redirect; response MIME,
  compression, version or envelope mismatch.

**The exact live root cause remains unverified.** There is no captured,
sanitized response evidence, and no live authentication request was authorized.
IP Guard might prevent the first connection, but neither its first-bind policy
nor the actual rejection was independently verified here.

## F. Smallest recommended correction — approval required

1. Consider adding **only `requestformat=JSON` to Legacy read-only form requests**,
   based on the official client evidence. Keep the supplied root endpoint,
   actions, credentials, TLS/DNS protections and REST behavior unchanged.
   Do not add an invented version field or API suffix.
2. Add bounded, redacted diagnostic reasons: transport status/MIME, failure
   stage, and vetted provider error codes. Do not log body, credentials, balance,
   personal data or arbitrary upstream messages.
3. Validate with offline request/parser tests. A real acceptance request must
   await explicit approval and originate from the intended server/IP—not Replit
   by default. Do not disable IP Guard.

Do not blindly accept HTML/XML, loosen version/account parsing, switch to the
PHP protocol or classify arbitrary provider messages as authentication failures.
If approved evidence instead confirms an IP Guard/configuration issue, use the
provider's approved configuration process; code alone cannot fix the IP binding.
