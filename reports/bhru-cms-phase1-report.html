BHRU: Subscriber Public Website
Branding & Hero Management

Implemented at CMS / Blog → Public Website, route /m/cms-blog-public-website, using the existing Subscriber Panel and workspace-tab system.

One frozen Public Template V2 remains shared by all subscribers. There are no separate subscriber website files. Public slug allocation/resolution, authentication, Platform Admin and licence/subscription behavior are unchanged.

1. Database/schema

Additive migration 005_subscriber_public_website.sql applied in Development through the existing explicit migration runner:

  • subscriber_public_sites: one subscriber-owned Branding/Hero configuration, revision counter and timestamps; no unrelated subscriber/account columns overloaded.
  • public_site_assets: owner, opaque generated key, validated type/size/dimensions. Composite foreign keys prevent cross-subscriber image references.
  • No CMS backfill required: existing subscribers retain truthful template defaults until their first explicit save. No subscriber, slug or licence migration updates.
  • Future CMS modules can add their own subscriber-scoped tables; none were implemented in this phase.

4. Persistent image storage

User-approved dedicated filesystem adapter, configured by BHRU_MEDIA_DIR. Development defaults to an ignored local directory. Production requires an absolute configured directory, a writable persistent mount and regular confirmation marker; no silent Development or temporary-directory fallback.

Required Dokploy setup is documented in BHRU_PUBLIC_MEDIA.md: named persistent volume bhru-public-media, recommended container target /var/lib/bhru/public-media, matching environment variable, UID/GID 1000:1000, confirmation marker, and coordinated PostgreSQL/media backups. No VPS host path is hardcoded.

Accepts PNG/JPEG ≤5 MiB, dimensions ≤4096 per side and ≤8 million pixels. Real decoding, CRC/structure checks, re-encoding and generated UUID keys reject corrupt/mismatched, animated, SVG, executable and trailing content. Original filenames are not storage authority; internal paths are never returned. Saved-image replacement commits before old unreferenced media cleanup.

Actual Dokploy volume setup, redeployment persistence and backup restoration remain operator prerequisites, not actions performed here. Interrupted processes can leave orphan files/uploads; no unattended garbage collector is introduced in Phase 1.

5. Subscriber isolation

CMS ownership comes only from the authenticated subscriber session and existing eligibility checks. Browser-supplied subscriber/slug fields and query parameters are rejected. Asset ownership is checked before preview/save; database foreign keys provide a second boundary. Reads, writes, uploads and cleanup remain owner-scoped. Public image/document handling does not switch visitor sessions.

Concurrent saves serialize: one current revision succeeds, the stale save returns 409. Subscriber session changes abort/drop obsolete UI work. Drafts remain component/session-scoped; no browser draft cache was added. Existing CSRF protections are retained, with explicit subscriber request headers on every CMS client call.

6. PublicSiteModel integration

The existing adapter loads CMS data using only the server-resolved public subscriber ID. Saved display name, primary colour, logo, description, hero badge/title/description/image and both CTAs are mapped into PublicSiteModel. Absent optional values use existing safe defaults. The preview invokes the exact same renderer and frozen CSS/menu script with validated unsaved values; only its preview security policy and temporary image URLs differ. No services, testimonials or business claims are fabricated.
