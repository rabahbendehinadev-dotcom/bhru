# BHRU public customer onboarding and reseller client management

## Implementation report

### 1. Existing architecture found
Migration 019 already provides tenant-scoped `public_customer_accounts` and
`public_customer_sessions`, scrypt passwords and a separate customer cookie
realm. Public auth runs before owner/admin middleware and uses existing public
eligibility and verified original-Host mapping. Clients/Suppliers was a
placeholder. E-Commerce Customers grouped existing order-contact snapshots.
No persisted reseller-client entity, customer wallet or payment ledger exists.

### 2. Root cause
Registering inserted a public customer account, but no Clients/Suppliers list
queried that table. The commerce contact list required an order and therefore
could never show a newly registered zero-order customer.

### 3. Canonical model chosen
The existing public customer account is also the owning reseller's registered
client. There is one identity, password, status and tenant-scoped profile.
No second identity table, registration synchronization job or duplicate CMS
client system was introduced.

### 4. Relationships
- Public Customer Account = registered Reseller Client, same UUID/row.
- Future authenticated retail orders reference that immutable account UUID.
- Guest Contact = an order-contact snapshot group, not an authenticated account.
- Matching guest email/phone is never evidence of account ownership and never
  triggers automatic adoption, rewriting or merging of historical orders.

### 5. Migration created
`lib/db/src/migrations/020_public_customer_onboarding.sql`.
It extends 019 additively, backfills client codes/usernames only, adds profile
columns, notes/activity/challenge tables and a nullable composite customer FK on
retail orders. It does not change old password hashes, old customer sessions,
existing order contacts, prices, money snapshots, licences or subscriptions.
Applied-file tracking/checksums make migration reruns safe; raw SQL is not meant
to be executed repeatedly outside the existing migration runner.

### 6. Every registration field
Account: email; optional username; required WhatsApp/mobile calling code and
national number; password and confirmation; preferred language; owning tenant's
enabled preferred currency; optional newsletter opt-in.
Billing: required first and last names; optional address lines 1/2; required
ISO 3166-1 alpha-2 country; optional state, city and postal code.
Verification: required Terms checkbox, challenge ID and user-entered answer.
Client code and consent timestamp are generated by the server, not submitted
as trusted browser values.

### 7. Username and client-code strategy
Client codes are eight uppercase alphanumeric characters (cryptographic random
hex for new accounts), immutable by a database trigger and unique per tenant.
Legacy accounts receive safe collision-retried codes and the code as username.
Blank new usernames default to the generated code. Usernames are 3–32 ASCII
letters/digits/hyphens/underscores, starting with a letter or digit, and unique
case-insensitively per tenant. Allocation/editing serializes on the subscriber
row and checks both username/code namespaces; database unique indexes guard
concurrent workers. Names/emails/phone do not determine identity.

### 8. WhatsApp/mobile normalization
The UI has explicit calling-code and national-number inputs. The server
normalizes separators and the `00` international prefix, requires an E.164
shape and uses `libphonenumber-js` to check possible number length/calling code
and store canonical `+...` format. Appropriate national-prefix normalization
comes from the phone library, not indiscriminate removal of leading zeros.
This is structural validation, not proof of WhatsApp ownership or an OTP check.
Legacy accounts may retain NULL phone until their profile is completed.

### 9. Multi-step registration
Account Information → Billing Details → Verification. Next validates its step;
Previous preserves inputs; completion validates the whole payload on the
server. Errors are visible, controls are labelled, progress is indicated and
focus moves between steps/errors. Registration retains the existing processed
response/sign-in handoff rather than introducing a new auto-login flow.

### 10. CAPTCHA/anti-bot
Server-generated six-character PNG challenge, ten-minute expiry, keyed
HMAC-hashed answer, tenant binding and HttpOnly browser-binding cookie.
`DELETE ... RETURNING` atomically consumes each attempted answer; invalid and
expired answers cannot be replayed. Solutions are never exposed in production
JSON, HTML, alt text or stored plaintext. Issuance and registration have
database-backed IP and tenant/IP limits. The browser refreshes the challenge
after an unsuccessful final submission.
This is a built-in image challenge, not an external managed bot-risk service.

### 11. Terms acceptance
`termsAccepted` must be true server-side. `terms_accepted_at` is recorded with
database time only when the new account is created. Old accounts remain NULL;
old consent is not invented or retroactively required for login.

### 12. Reseller list columns
Client / Email (full name and email), Code, Username, WhatsApp, Location
(city/country), Status, Currency, Orders, Balance, Due, Joined, Actions.
Name/code and View / Manage open the dedicated client detail. Refresh is
available even when the list is already open; zero-order clients are included.

### 13. Search, filters and pagination
Server-side search: username, client code, first/last/full name, email and
normalized/formatted WhatsApp. Filters: all registered clients, Active,
Blocked. Thirty rows per page with Previous/Next, deterministic ordering,
bounded validated inputs and escaped LIKE parameters. Only this reseller's
canonical accounts are returned.

### 14. Routes
List: `/m/clients`. Detail: `/m/clients/{customerId}`.
The old `/m/view-search-clients` address redirects to the canonical list.
Nested client pages are explicit retained workspace tabs, not a general
wildcard that absorbs public/admin namespaces.

### 15. Detail sections
Summary uses initials, name, code, email and active/blocked status.
Tabs: Overview, Financial, Profile, Orders, Activity, Notes.
Overview/profile include contact, billing, location, registration/login dates,
language and stored/effective currency. Profile editing excludes password,
email, client code, account UUID, Terms timestamp and ownership/security fields.
Orders use real retail snapshots; activity uses actual successful actions;
notes are internal reseller-only data.

### 16. Financial balance/due
No real ledger exists. The dedicated financial-summary boundary returns
available balance, locked amount and due as explicit zero with
`ledgerAvailable:false`. Display uses the existing currency formatter and the
effective enabled currency. There are no fabricated wallet entries, invoices,
paid totals, credits or receipts. Retail order amounts are not mislabeled paid
spending. No currency calculations or architecture were changed.

### 17. Order association
For a new public retail checkout, the server resolves the customer session in
the store's tenant, rechecks an enabled canonical account under a row lock and
writes `store_orders.customer_id`. Composite `(subscriber_id,customer_id)` FK
rejects foreign-tenant associations. No browser-supplied customer ID is accepted.
Existing checkout, stock, prices, receipt snapshots and order status behavior
remain unchanged. Profile edits never rewrite historical contact/money values.

### 18. Guest checkout
Guest checkout still creates an order with NULL customer ID. Old guest orders
are untouched. A retry of an existing guest checkout key after login cannot
silently adopt it: identity-sensitive idempotency rejects that changed request.

### 19. E-Commerce Customers
Registered clients reuse the canonical client table, including zero-order
accounts. Guest contacts remain a separate labelled view querying only orders
with NULL customer ID. The registered and guest views are not duplicate
authentication identities.

### 20. Blocking
Owning reseller can block/reactivate. Blocking changes the existing account
enabled flag and deletes that account's tenant-scoped customer sessions in one
transaction. Login checks enabled under a lock; customer-session lookup also
checks it, so outstanding sessions are revoked/rejected. History, orders,
profile and notes remain intact. Reactivation requires a fresh login.

### 21. Login identifiers
Existing email login remains; the same field additionally accepts case-insensitive
tenant-scoped username or client code. Failures remain generic. Customer
cookies, signature realm, hashes and login handoff are not replaced.

### 22. Phase 1 compatibility
Migration 019 and password/security primitives are unchanged. Existing account
IDs, emails, hashes and unexpired sessions survive; extended legacy fields are
NULL/default without requiring re-registration. Existing public auth headers,
mobile customer links and logged-out CMS preview behavior remain compatible.
Successful logins now record actual last-login time and an activity event.

### 23. Same email across subscribers
The existing `(subscriber_id,email)` uniqueness is preserved. The same email
and username may register under two subscribers as distinct tenant-owned
accounts. This is exercised in the real-SQL focused checks.

### 24. Tenant isolation
Private list/read/edit/status/note ownership comes from the existing signed
reseller session, never a body tenant ID. All queries bind both subscriber and
account where relevant. Public tenant resolution keeps the existing original
Host/verified-domain and public eligibility policy. Public account payloads use
an allowlist: no account UUID, subscriber UUID, hashes, session data or internal
notes are exposed. Customer cookies cannot authorize reseller/admin endpoints.

### 25. Login-as-client
Explicitly deferred. No fake button or unsafe reuse of owner/customer sessions
was added. A future implementation needs a separate short-lived, audited
impersonation realm and a clear stop/return flow.

### 26. Files changed
The exact feature-file inventory is listed below. Generated API clients and Zod
schemas are regenerated from OpenAPI. Pasted attachments, memory and unrelated
metadata were not modified or included. No commit or push was made.

### 27. Migration filename and operator requirement
`020_public_customer_onboarding.sql`. Apply through the existing `db:migrate`
procedure only as part of a separately authorized rollout. Existing startup
guards now require the new profile columns/tables/order association column.
No production migration or deployment was performed.

### 28. Focused validation
The focused runner creates an entirely separate Unix-socket-only PostgreSQL
cluster under `/tmp`, applies the old migrations, creates synthetic fixtures,
upgrades with the actual compiled migration runner and reruns it. It explicitly
replaces any supplied DATABASE_URL with its temporary cluster's URL.
The tests use actual HTTP routes, SQL, constraints, locks, signing, hashing and
PNG generation. Test-only temporary-bundle instrumentation captures challenge
solutions; no solution/debug hooks exist in production source or build.
All 20 focused SQL/HTTP test groups pass. Coverage includes the requested backend
acceptance cases, plus immutable code,
challenge binding/expiry/replay, concurrent allocation, private profile edits,
notes, disabled-currency fallback, snapshot preservation, logout and CSP/script
syntax. No browser/E2E/full regression suite was run.

Commands:
```sh
pnpm --filter @workspace/api-server run build
node scripts/test-public-customer-onboarding.mjs
# Compatibility entry point, same focused runner:
node scripts/test-public-customer-auth.mjs
pnpm --filter @workspace/api-server run typecheck
pnpm --filter @workspace/bhru run typecheck
pnpm --filter @workspace/bhru run build
```
The runner needs PostgreSQL CLI tools (`initdb`, `pg_ctl`) on PATH.
Backend typecheck/build and frontend production build pass. Frontend full
typecheck reports only the existing unrelated E-Commerce type mismatch.
Visual responsiveness and interactive browser acceptance remain manual.

Preview startup was checked after the changes: the frontend workflow runs, but
the API stops at the existing database/migration guard (`Database is unavailable
or migrations have not been applied. Run db:migrate before starting.`). The
Preview screenshot therefore shows HTTP 502, not the new authenticated pages.
No migration, fixtures, guard bypass or environment change was applied to its
configured database. This does not claim that Preview or the live VPS has passed
interactive acceptance.

### 30. Environment variables
No new production environment variables or provider credentials.
Continue using the existing PostgreSQL `DATABASE_URL`, `SESSION_SECRET` (at
least 32 characters), `PLATFORM_ADMIN_PATH`, platform-host/custom-domain and
media configuration. The CAPTCHA uses a separate HMAC purpose with the
existing secret; no WhatsApp OTP credentials or CAPTCHA-provider key is needed.
No environment, domain infrastructure, storage mount or production config was
changed.

### 31. Limitations / future phase
- Financial wallet/ledger, invoice/receipt payments and safely paid spending
  totals do not exist and were not invented.
- Only existing retail orders are shown; no pretend IMEI/server/remote systems.
- Detail returns the latest 30 orders and 50 activity/notes entries; summary
  counts cover all linked retail orders. Larger-history paging can follow.
- No WhatsApp ownership OTP, customer self-editing, password recovery,
  email-confirmation service, social auth or impersonation was introduced.
- The built-in CAPTCHA does not replace a managed anti-bot/risk service;
  an accessible non-visual challenge/provider can be evaluated separately.
- Live VPS DB/TLS and browser acceptance require a separately approved rollout.
  Local focused tests do not claim live production acceptance.
- Replit's source-only Preview must not be mistaken for the actual VPS database.
  An unmigrated/unavailable Preview API is not bypassed or filled with fake
  customer data to make screenshots look functional.

## Manual acceptance path
In an authorized environment with migration 020 applied:
1. Visit `/{public_slug}/customer/register` (or verified custom host
   `/customer/register`), complete the three steps and sign in.
2. Open reseller Clients/Suppliers → View / Search Clients (`/m/clients`).
   Refresh an already-open list; check the new zero-order client and search.
3. Open its profile; inspect tabs, edit non-security details, add a note,
   block/reactivate and verify the customer session/login behavior.
4. Place one logged-in retail order and one guest order with matching contact
   values; verify only the authenticated order appears on the client.
5. Check E-Commerce → Customers → Registered clients / Guest contacts.

Stop after review. No production migration, VPS/Dokploy access, push, history
rewrite or deployment is authorized by this implementation report.
