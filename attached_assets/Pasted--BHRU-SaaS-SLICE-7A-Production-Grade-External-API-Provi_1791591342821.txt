## 2.1 DHRU Fusion Pro REST Reseller API

Documented API base pattern:

`https://YOUR-WORKSPACE-DOMAIN/api/reseller/v1`

Authentication:

`Authorization: Bearer <API_TOKEN>`

`Accept: application/json`

Documented read endpoints:

- `GET /account`
- `GET /products`
- `GET /products?product_id=...`
- `GET /order?order_uuid=...`

Documented write endpoint:

- `POST /order`

The `/products` response contains categories and products. Product entries are keyed by upstream product ID and can contain type, category IDs, price, delivery time and required fields.

Responses use a JSON envelope with `status`, `message`, `code` and `data`.

The API token is NOT interchangeable with a separately generated API key.

The token may be restricted by expiry, source IP and wallet currency.

For Slice 7A, implement ONLY the required read operations. Never call `POST /order`.

## 2.2 DHRU Fusion Legacy API

The legacy API uses operations such as:

- `accountinfo`
- `imeiservicelist`
- `placeimeiorder`
- `placeimeiorderbulk`
- `getimeiorder`
- `getimeiorderbulk`

It may use username/API access key authentication and a different request/response envelope.

Do not assume legacy and modern REST protocols are interchangeable.

## 2.3 Fusion Pro Simple API Request Listener

This repository demonstrates an upstream-side custom request listener with actions such as:

- `account_info`
- `products`
- `place-order`

This is NOT automatically the same protocol as the Fusion Pro Reseller REST API.

Do not implement this protocol as a working BHRU upstream adapter without confirming the complete contract.

# 4. SECURITY AND CREDENTIAL STORAGE

This is a security-sensitive integration.

Requirements:

1. Never store provider tokens or API keys in plaintext.
2. Use authenticated encryption at rest with a dedicated server-side encryption key and versioned key metadata.
3. Do not silently reuse payment gateway encryption keys.
4. Do not generate a new encryption key on each application restart.
5. Never send decrypted credentials to the frontend.
6. Never include credentials in API responses, audit logs, browser storage or application error messages.
7. Support secure credential replacement without revealing existing values.
8. Mask saved credential fields in the UI.
9. Redact Authorization headers and sensitive URL parameters from logs.
10. Do not accept arbitrary HTTP headers or request bodies from users as part of connection testing.
11. Protect connection-test and sync endpoints against CSRF and unauthorized access according to existing application conventions.
12. Rate-limit connection testing and sync requests.

If the encryption key is not configured:

- Keep the system fail-closed.
- Explain the missing configuration.
- Never silently fall back to plaintext storage.
- Never log the missing key's value.

## SSRF and Network Protection

A Reseller-supplied API URL is untrusted.

Implement robust outbound HTTP safeguards:

- HTTPS required.
- Reject credentials embedded in URLs.
- Reject localhost, loopback, private, link-local, multicast and metadata IP ranges.
- Reject internal hostnames and unsupported ports.
- Validate DNS resolution and prevent DNS rebinding.
- Revalidate every redirect or preferably disable redirects.
- Enforce safe destination resolution at actual connection time.
- Apply bounded timeouts and response-size limits.
- Do not permit arbitrary proxy configuration.
- Do not follow URLs supplied inside upstream response bodies.

If the runtime cannot enforce safe destination IP binding, use an appropriately restricted outbound network mechanism or disable arbitrary custom endpoints until a safe implementation is possible.

Do not describe an ordinary pre-request DNS check as complete SSRF protection.
