CURRENT BHRU RULES THAT MUST BE PRESERVED
==================================================

- public_customer_accounts is the canonical client identity
- do not create a duplicate customer/client identity table
- client Account Currency is immutable
- wallet/account currency must match Account Currency
- reseller controls which currencies appear during registration
- wallet ledger already exists
- service orders already debit wallet atomically
- refunds restore the exact original account-currency amount
- order price/currency snapshots are immutable
- tenant isolation is mandatory
- retail/e-commerce orders remain separate
- guest checkout remains separate
- customer sessions already exist
- client Financial / Activity / Notes tabs already exist
- customer Wallet / Transactions pages already exist
- no provider API integration yet

==================================================
PART A — FINANCIAL SEMANTICS
==================================================

For each financial concept below, define:

- business meaning
- whether it is stored or derived
- authoritative source
- whether it can be negative
- whether it affects spendability
- when it changes
- what event changes it
- whether customer sees it
- whether reseller sees it
- whether it appears on Dashboard
- whether it appears on Statement
- whether it belongs to prepaid wallet or credit facility

Analyze:

AVAILABLE BALANCE
Money the customer can spend immediately.

LOCKED BALANCE
Money reserved for in-progress operations, if BHRU actually needs this concept.

DUE
Do NOT keep this as a fake zero metric.

Define whether Due should mean:
- unpaid debt
- outstanding invoices
- consumed credit line
or something else.

If BHRU has no real Due facility yet, recommend whether Dashboard should hide it until implemented.

CREDIT LIMIT
Maximum reseller-approved credit facility.

USED CREDIT
Current amount owed under credit facility.

AVAILABLE CREDIT
Credit Limit - Used Credit.

TOTAL CREDITS
All positive wallet/financial ledger movements that qualify as credits.

TOTAL DEBITS
All negative wallet/financial ledger movements.

TOTAL SPENT
Only successful service-order spending, not every debit.

PENDING FUNDING
Customer funding requests awaiting approval/payment confirmation.

REFUNDS
Exact restoration of prior charge amount/currency.

ADJUSTMENTS
Manual reseller/admin balance changes.

PART B — PREPAID WALLET VS CREDIT FACILITY
==================================================

Design a clean separation between:

A. PREPAID WALLET
Customer's own deposited/credited money.

B. CREDIT FACILITY
Optional reseller-issued debt/credit line.

Do NOT mix them into one ambiguous number.

Recommend whether BHRU should use separate authoritative balances/tables for:

- prepaid wallet balance
- reserved/locked wallet amount
- credit limit
- credit used

Define order spending precedence if credit is enabled later.

Example possibilities:

1. wallet only
2. wallet first then credit
3. credit only for approved groups/clients

Do NOT implement.
Recommend the safest future model.

==================================================
PART G — FUNDING / PAYMENT BOUNDARY
==================================================

Design future boundaries now, without implementing.

Clearly separate:

1. Funding Request
Customer asks to add money.

2. Payment Transaction
Actual external/internal money movement.

3. Wallet Ledger
Internal financial effect on customer's account.

Example:

Customer submits funding request
→ reseller verifies payment
→ payment transaction recorded
→ wallet ledger credit posted
→ funding request marked approved

Define idempotency boundaries.

Prevent a payment from crediting wallet twice.

==================================================

Define relationship between:

Recommend whether service orders should always generate invoices or only optionally.

Consider server-business workflows where many small orders happen from wallet balance.

Likely:
- wallet statement for all financial movements
- invoice optionally for funding / grouped billing / formal business needs

Analyze and recommend.

- financial ledger

Audit/activity records should reference financial objects rather than replacing them.

Define event categories:

- login failure
- logout
- password changed
- password recovery
- session revoked
- all sessions revoked
- 2FA enabled/disabled
- blocked login

PROFILE
- profile changed
- phone changed
- address changed
- notification preference changed

ACCOUNT
- account created
- account activated
- account blocked
- account unblocked
- verification status changed
- client group changed
- service-access policy changed

FINANCIAL
- wallet adjusted
- funding request created/approved/rejected
- payment recorded
- refund processed
- credit facility changed

ORDER
- service order created
- processing
- completed
- rejected
- cancelled

API
- API enabled/disabled
- API key generated/rotated/revoked
- IP whitelist changed

PART R — INVARIANTS
==================================================

Define explicit invariants BHRU must enforce.

Examples:

- wallet currency == customer Account Currency
- posted ledger entries are immutable
- balance-changing operation and ledger record commit atomically
- no wallet mutation without ledger entry
- refund cannot exceed/refund original charge twice
- manual adjustment requires reason and actor
- cross-tenant financial references forbidden
- payment transaction credits wallet at most once
- client account currency never changes implicitly

Create a strong invariant list.
