DHRU Fusion.

Each Reseller chooses from those gateways and enters
their own API credentials.

Customers use Wallet → Add Funds to pay through
the Reseller's configured gateway.

========================================================
PHASE 2 — PAYMENT ADAPTER CONTRACT
========================================================

Implement a strongly typed provider adapter interface.

Each adapter should support, where applicable:

validateConfiguration()
createPayment()
getPaymentStatus()
verifyWebhook()
normalizeWebhookEvent()

Optional capabilities:

cancelPayment()
refundPayment()
getSupportedCurrencies()

Each adapter must declare its capabilities explicitly.

Never assume every gateway supports every operation.

The adapter contract must support:

- provider payment identifier
- provider merchant/account identifier
- payment URL when available
- payment address when applicable
- expected payment amount
- payment currency
- expiry timestamp
- provider-specific opaque metadata

Provider-specific metadata must be validated,
bounded and safely stored.

Do not expose secrets or internal provider data
to the customer.

========================================================
PHASE 3 — PAYMENT INITIATION SERVICE
========================================================

Build a reusable payment initiation service.

Workflow:

1. Authenticate customer.
2. Resolve tenant from trusted existing context.
3. Verify customer account eligibility.
4. Verify selected gateway is globally enabled.
5. Verify gateway adapter is implemented.
6. Verify Reseller enabled the gateway.
7. Verify valid configuration exists.
8. Verify amount and currency eligibility.
9. Generate authoritative server-side quotation.
10. Freeze commercial/FX/fee snapshot.
11. Create funding request.
12. Invoke provider adapter.
13. Persist provider payment identity.
14. Return safe payment instructions or payment URL.

IMPORTANT:

Never trust frontend-calculated amounts.

Never allow the customer to supply an arbitrary
wallet credit amount after quotation.

The server must recalculate and validate everything.

========================================================
PHASE 4 — INITIATION IDEMPOTENCY
========================================================

Prevent duplicate provider payment creation.

Use a customer/tenant-scoped idempotency key.

Repeated initiation with the same key must return
the existing safe payment result.

Do not create another funding request or another
provider payment for an identical accepted request.

Handle concurrency correctly.

Do not hold a PostgreSQL transaction open across
slow external provider HTTP calls.

Use an explicit initiation state/lease mechanism
where needed.

If provider creation succeeds but database persistence
fails, provide a safe recovery path.

Do not silently create orphaned payment obligations.

========================================================
PHASE 5 — PAYMENT STATUS LIFECYCLE
========================================================

Implement strict state transitions.

Funding request:

CREATED
PENDING_PAYMENT
PAID
FAILED
EXPIRED
CANCELLED

Payment processing may additionally require
internal intermediate states.

Do not overload customer-visible states with
technical processing details.

Only verified settlement may mark funding PAID.

Reject impossible transitions.

Examples:

PAID → PENDING_PAYMENT
must be rejected.

PAID → EXPIRED
must be rejected.

CANCELLED → PAID
must not automatically credit without an
explicit documented recovery policy.

PHASE 6 — WEBHOOK ROUTING
========================================================

Prepare a secure provider-specific callback router.

Suggested conceptual route:

/api/payments/webhooks/:gatewayCode

Use the project's existing API routing conventions.

Do not invent provider-specific webhook protocols.

Each installed adapter must explicitly implement
its own authentication verification.

Requirements:

- raw request body access where required
- provider-specific signature verification
- constant-time comparison where applicable
- strict request size limits
- timestamp validation where supported
- replay protection
- trusted merchant/configuration resolution
- tenant isolation
- bounded payload handling
- safe logging

A gateway without an implemented verifier
must never be able to settle a payment.

Unknown gateway callbacks must fail closed.

Never trust:

payment_success=true

or customer browser redirects.

========================================================
PHASE 7 — VERIFIED EVENT NORMALIZATION
========================================================

Normalize authentic provider events into a
strict internal verified-payment structure.

Include:

- gateway identity
- merchant/configuration identity
- provider transaction identity
- funding request identity
- actual paid amount
- actual payment currency
- verification timestamp
- verification method
- bounded provider event reference

Only trusted adapters can create verified events.

Never accept a public JSON body claiming
to be an already verified receipt.

========================================================
PHASE 8 — AMOUNT AND CURRENCY VERIFICATION
========================================================

Use exact decimal/minor-unit arithmetic.

Compare:

Expected payment amount
Actual provider-confirmed amount

Expected currency
Actual provider-confirmed currency

Expected merchant
Actual provider-confirmed merchant

Expected funding request
Actual provider-confirmed reference

Do not credit on mismatches.

Partial payments must not be silently treated
as full payments.

Overpayments must not silently increase wallet credit.

Record discrepancies for manual review.

Do not automatically refund or reallocate them.

========================================================
PHASE 9 — DURABLE WEBHOOK PROCESSING
========================================================

Persist authenticated callback events durably.

Separate:

Webhook received
Webhook authenticated
Payment verified
Payment settled

Do not conflate these stages.

A successful HTTP response to a provider must
not imply that the wallet was credited unless
settlement actually succeeded.

Support safe retry processing for verified
but unsettled payment receipts.

Retries must preserve exact original snapshots.

========================================================
PHASE 10 — SETTLEMENT INTEGRATION
========================================================

Reuse the existing Slice 5A settlement kernel.

Do not implement another wallet credit path.

Verified payment settlement must atomically:

- lock funding request
- validate expected state
- lock customer wallet
- validate account currency
- validate verified receipt
- credit exact frozen wallet amount
- insert immutable ledger entry
- mark payment SETTLED
- mark funding request PAID
- record Activity event

Preserve:

- no double credit
- tenant isolation
- exact account currency
- immutable ledger
- reconciliation consistency
- transaction rollback

========================================================
PHASE 11 — BACKGROUND RETRY PROCESSING
========================================================

Implement a bounded retry mechanism for:

- provider initiation recovery
- authenticated callback processing
- verified but unsettled receipts
- transient provider status checks

Use database-backed retry state where appropriate.

Support:

- retry count
- next retry time
- last safe error category
- maximum attempts
- manual review after exhaustion

Do not require Redis or a new external service
unless the existing architecture already needs it.

Do not create infinite retry loops.

========================================================
PHASE 12 — SAFE WORKER EXECUTION
========================================================

BHRU may run multiple application replicas
under Dokploy/Docker Swarm.

Background processing must therefore be safe
under concurrent workers.

Use PostgreSQL locking/leases where appropriate.

Examples:

FOR UPDATE SKIP LOCKED

or equivalent safe mechanisms.

Prevent two replicas from processing the same
payment obligation simultaneously.

Workers must be bounded and restart-safe.

Do not introduce a second independent payment
settlement authority.

========================================================
PHASE 13 — PAYMENT EXPIRY
========================================================

Implement expiry handling for unpaid requests.

Requirements:

- expiry based on trusted server time
- no wallet credit for an unverified payment
- PAID requests never expire retroactively
- idempotent expiry processing
- safe handling of late provider notifications

IMPORTANT:

A provider-confirmed late payment must not be
silently discarded or silently credited against
an expired/cancelled request.

Record it for explicit review according to
the documented recovery policy.
