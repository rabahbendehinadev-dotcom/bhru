DHRU Fusion.

public_customer_accounts

- Service groups

- Atomic wallet debits and exact refunds
- Immutable wallet ledger
- Financial reconciliation
- Client Activity audit

029_payment_processing_infrastructure.sql

========================================================
PRIMARY OBJECTIVE
========================================================

Implement a complete tenant-scoped customer
grouping and service pricing system.

A Reseller must be able to:

1. Create customer groups.
2. Edit customer groups.
3. Activate/deactivate groups.
4. Assign customers to groups.
5. Define default pricing rules.
6. Define group-specific pricing rules.
7. Define customer-specific service prices.
8. Preview the effective price for a customer.
9. Preserve historical order prices.
10. Manage everything from the existing
    Reseller dashboard.

Customers must automatically receive the
correct effective service price.

No customer may choose their own group or
override their service price.

========================================================
PHASE 2 — CUSTOMER GROUP MODEL
========================================================

Implement customer groups.

Suggested fields:

id
subscriber_id
name
description
is_active
is_default
sort_order
created_at
updated_at

Every group belongs to exactly one Reseller.

Group names must be unique within the same tenant.

Different Resellers may use identical names.

Examples:

Normal
VIP
Wholesale
Premium

Do not hardcode these names as mandatory groups.

========================================================
PHASE 3 — DEFAULT GROUP
========================================================

Each Reseller should have one default group.

Requirements:

- New customers automatically join the default group.
- Existing customers without a group are handled safely.
- Reseller can choose another default group.
- Exactly one active default group per tenant.
- Default group cannot be deleted or disabled
  without selecting a replacement.
- Changing the default group must not silently
  reassign existing customers.

Do not make assumptions about historical customers.

If a migration/backfill is required, use a
documented, deterministic and tenant-safe policy.

========================================================
PHASE 4 — CUSTOMER GROUP ASSIGNMENT
========================================================

Add group assignment to:

Reseller → Clients

And:

Reseller → Client Detail

Allow:

- Assign one customer to a group.
- Change customer group.
- Filter customers by group.
- Display current group.
- Show group in customer Overview.

Only authorized Reseller users may modify it.

Customers cannot assign themselves.

Changing a group affects future quotations
and future orders only.

Existing orders remain unchanged.

========================================================

- Group list

Use compact professional styling.

Do not redesign unrelated navigation.

========================================================
PHASE 6 — PRICING RULE MODEL
========================================================

Implement group pricing rules.

A pricing rule must belong to:

subscriber_id
customer_group_id

and target an authoritative service.

Support pricing methods:

1. INHERIT_DEFAULT
2. FIXED_PRICE
3. PERCENT_DISCOUNT
4. PERCENT_MARKUP

Avoid redundant stored rules for inheritance
where possible.

Rules must be deterministic and validated.

Do not allow negative final service prices.

Do not allow unbounded or invalid percentages.

========================================================
PHASE 7 — CUSTOMER-SPECIFIC PRICING
========================================================

Support a direct price override for one customer.

Suggested model:

subscriber_id
customer_id
service_id
pricing_method
pricing_value
created_at
updated_at

Customer-specific pricing takes precedence
over group pricing.

Only the customer's Reseller can configure it.

Customer cannot edit their own price.

Use strict tenant/customer/service validation.

========================================================
PHASE 8 — PRICE PRECEDENCE
========================================================

Implement one authoritative pricing precedence:

1. Customer-specific service rule
2. Customer group service rule
3. Standard Reseller service price

Examples:

Standard service price:
10.00 USD

VIP group:
10% discount

Customer-specific:
8.00 USD

Effective price:
8.00 USD

If no customer override exists:

Effective price:
9.00 USD

If no group rule exists:

Effective price:
10.00 USD

Do not apply group and customer rules
cumulatively unless explicitly specified.

========================================================
PHASE 9 — PRICING CURRENCY
========================================================

Preserve the existing immutable Account Currency.

The service catalog currently uses a base
pricing currency.

Audit the actual authoritative base-currency
and FX implementation before changing anything.

Pricing rules must have unambiguous units.

Recommended:

- Fixed-price rules use the authoritative
  service pricing currency.

- Percentage rules operate on the authoritative
  standard service price before FX conversion.

- Convert the final effective service price
  once into the customer's Account Currency.

Use the existing reseller-approved FX rates.

Never convert wallet balances.

Never perform double FX conversion.

Never use JavaScript floating-point arithmetic
for financial calculations.

Use exact decimal/minor-unit arithmetic.

========================================================
PHASE 10 — PRICE SNAPSHOTS
========================================================

At order placement, freeze:

- Standard service price
- Effective service price
- Pricing rule source
- Customer group at ordering time
- Customer-specific override identifier
  when applicable
- FX rate snapshot
- Final charged Account Currency amount

Only add snapshot fields where necessary.

Do not rewrite old order snapshots.

Never recalculate historical orders using
current group membership or current prices.

========================================================
PHASE 11 — SERVICE CATALOG INTEGRATION
========================================================

The authenticated customer service catalog
must display the effective customer price.

Apply the same effective price in:

- service list
- service details
- order quotation
- order confirmation
- order placement

Do not show standard prices to VIP customers
when their effective price is different.

Do not expose other customers' pricing rules.

========================================================
PHASE 12 — ORDER PLACEMENT INTEGRATION
========================================================

The backend must independently calculate
the effective service price.

Never trust frontend-submitted prices.

Order placement must:

1. Resolve authenticated customer.
2. Resolve tenant.
3. Resolve current group.
4. Resolve customer-specific pricing rule.
5. Resolve group pricing rule.
6. Calculate effective price.
7. Apply existing FX conversion once.
8. Freeze price snapshot.
9. Validate wallet balance.
10. Atomically create order and debit wallet.
11. Insert immutable ledger entry.
12. Record Activity event.

Preserve existing idempotency and locking.

========================================================
PHASE 13 — PRICING CONSISTENCY
========================================================

Use one shared pricing engine.

The same customer/service must receive the
same price across:

- customer catalog
- customer quote
- customer order placement
- reseller effective-price preview

Do not maintain separate pricing formulas
in frontend and backend.

All authoritative calculations belong
on the server.

========================================================
PHASE 17 — INACTIVE GROUPS
========================================================

Define deterministic behavior for inactive groups.

Recommended:

- Existing customers retain their historical
  group assignment.
- Inactive groups cannot be assigned to
  new customers.
- Existing customers in inactive groups
  fall back to standard service pricing
  unless an explicit customer override exists.
- Reseller UI clearly shows inactive status.

Do not silently change existing group IDs.

Document this behavior.

========================================================
PHASE 18 — DELETION SAFETY
========================================================

Do not hard-delete groups that are referenced
by customers or historical pricing snapshots.

Prefer safe deactivation.

Allow deleting an unused group only if it
cannot break historical references.

Do not cascade-delete customer accounts,
orders, wallet records or ledger entries.
