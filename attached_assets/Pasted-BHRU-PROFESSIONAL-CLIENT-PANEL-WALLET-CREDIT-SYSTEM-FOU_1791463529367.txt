==================================================
BUSINESS MODEL
==================================================

A BHRU reseller operates a server/panel.

Public customer flow must become:

REGISTER
→ LOGIN
→ VIEW SERVICES
→ CHECK BALANCE
→ RESELLER FUNDS CUSTOMER
→ CUSTOMER PLACES ORDER
→ BALANCE IS DEDUCTED
→ ORDER IS PROCESSED
→ IF REFUNDABLE FAILURE/REJECTION OCCURS, CREDIT IS RESTORED
→ ALL MONEY MOVEMENTS ARE AUDITABLE

For server-type services, the customer must NOT be able to purchase without sufficient wallet balance.

This applies conceptually to:
- IMEI services
- Server services
- File services
- Remote services
- future API-imported services

Retail / E-Commerce guest checkout must remain separate unless explicitly changed later.

==================================================
4. STRICT MONEY RULES
==================================================

Use safe monetary handling.

Do NOT use JavaScript floating point for financial calculations.

Follow BHRU's existing integer/minor-unit or exact-decimal monetary architecture.

All wallet mutations must be atomic database transactions.

Critical rule:

Customer balance must NEVER accidentally become negative.

For a normal customer:

available_balance >= order_price

must be checked and deducted atomically.

Avoid race conditions where two simultaneous orders can spend the same balance.

Use:
- transaction
- row lock / appropriate PostgreSQL locking
or equivalent safe concurrency control

according to the existing DB architecture.

==================================================
10. ATOMIC ORDER PURCHASE
==================================================

Order creation and wallet deduction must be one atomic business operation.

Preferred behavior:

BEGIN TRANSACTION

1. Resolve tenant/client from authenticated session.
2. Resolve service and server-calculated selling price.
3. Lock/read customer wallet safely.
4. Verify sufficient funds.
5. Create order.
6. Deduct wallet balance.
7. Create ledger order_debit entry referencing order ID.
8. Commit.

If any step fails:
ROLLBACK everything.

Never allow:
- order without debit
- debit without order

Do NOT automatically refund every failure status blindly.

Inspect current order status architecture first.

Define explicit refundable states.

Refund operation must be idempotent.
