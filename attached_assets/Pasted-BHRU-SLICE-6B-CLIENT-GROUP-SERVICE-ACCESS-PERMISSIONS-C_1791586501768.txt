========================================================
PRIMARY OBJECTIVE
========================================================

Implement a complete, secure, tenant-scoped
service-access control system.

A Reseller must be able to control which
services are available to:

1. All customers
2. A specific customer group
3. One individual customer

Access control must apply to:

- Customer service catalog
- Service category navigation
- Service search
- Service details
- Service quotations
- Order confirmation
- Order placement
- Direct API requests

The backend must be authoritative.

Hiding a service in the frontend is NOT
sufficient security.

========================================================
PHASE 2 — ACCESS POLICY DESIGN
========================================================

Implement a clear three-level access model:

LEVEL 1:
GLOBAL SERVICE AVAILABILITY

LEVEL 2:
CUSTOMER GROUP ACCESS POLICY

LEVEL 3:
INDIVIDUAL CUSTOMER ACCESS OVERRIDE

A service must first be globally available
under the existing reseller catalog rules.

Group/customer permissions must NEVER
override a globally disabled service.

The same applies to disabled service categories.

========================================================
PHASE 3 — ACCESS PRECEDENCE
========================================================

Implement deterministic access precedence.

First evaluate hard global restrictions:

- Service exists
- Service belongs to the tenant's
  authorized catalog
- Service is globally enabled
- Parent category/group is enabled
- Existing service eligibility requirements pass

If any hard restriction fails:

ACCESS DENIED.

No group or customer rule can override it.

Otherwise apply:

1. Individual customer explicit DENY
2. Individual customer explicit ALLOW
3. Active customer group explicit DENY
4. Active customer group explicit ALLOW
5. Existing default service availability

Individual customer rules override
group-level rules.

The order above expresses this clearly.

Important:

An explicit customer ALLOW can override
a group DENY, but cannot override a
globally disabled service or category.

Do not let group/customer policies
bypass existing platform-wide restrictions.

========================================================
PHASE 4 — DEFAULT BEHAVIOR
========================================================

Backward compatibility is critical.

If no group/customer access rule exists:

Use the existing service availability behavior.

Do NOT suddenly hide existing services
from existing customers.

Do NOT introduce an implicit deny-all
policy during migration.

Existing resellers must retain their
current service visibility by default.

The default behavior should be:

INHERIT_EXISTING_AVAILABILITY

PHASE 5 — POLICY MODEL

Implement tenant-scoped service-access policies.

Subject types:

Access effects:

ALLOW

Use the actual existing customer-group,

Do not blindly assume column types.

Enforce unique policies for:

tenant + subject + service

A foreign-tenant customer, group or service
must never be accepted.

Use foreign keys and database constraints
where practical.

If the schema requires separate policy
tables for strong referential integrity,
prefer that over an unsafe polymorphic design.

========================================================
PHASE 6 — CATEGORY-LEVEL POLICIES
========================================================

Support category-level access rules if
compatible with the existing category model.

A Reseller should be able to:

- Allow a category for a group
- Deny a category for a group
- Allow a category for one customer
- Deny a category for one customer
- Inherit existing availability

Category rules affect services contained
in that category.

However:

An explicit service-level policy should
be able to override a configurable
category-level policy.

Example:

VIP group:
Category IMEI Checks = DENY

Specific service:
Premium IMEI Check = ALLOW

Result:
Only Premium IMEI Check is available
from that category, provided the category
is globally enabled.

Important distinction:

A globally disabled category is a
hard restriction and cannot be overridden.

A configurable category access DENY is
a soft policy and may be overridden by
a more specific service ALLOW.

========================================================
PHASE 8 — POLICY SPECIFICITY
========================================================

Use the following rule specificity
within the same subject:

1. Service-specific policy
2. Category-specific policy
3. Inherit existing availability

Subject precedence:

1. Individual customer
2. Active customer group
3. Existing default behavior

Examples:

A customer service-level ALLOW overrides
their own category-level DENY.

A customer category-level DENY overrides
a group service-level ALLOW.

A customer explicit rule overrides a
group rule, subject to global restrictions.

Document this exact behavior.

Avoid contradictory precedence between
different endpoints.

========================================================
PHASE 9 — INACTIVE CUSTOMER GROUPS
========================================================

Slice 6A allows existing customers
to remain assigned to inactive groups.

Preserve that behavior.

An inactive group must not grant
new service permissions.

Recommended behavior:

- Existing group membership remains stored.
- Inactive group access policies are ignored.
- Individual customer policies remain valid.
- Existing global service availability applies
  when no individual rule exists.

Do not automatically move customers
to another group.

Do not modify historical group assignments.

========================================================
PHASE 16 — QUOTATION SECURITY
========================================================

Before generating a service quote:

1. Resolve authenticated customer.
2. Resolve authoritative tenant.
3. Resolve current customer group.
4. Resolve global service availability.
5. Resolve customer/group access policy.
6. Reject if access is denied.
7. Calculate effective price using Slice 6A.
8. Apply approved FX once.
9. Return controlled quotation.

Never calculate a quotation for a
forbidden service.

Do not change the pricing precedence
from Slice 6A.

========================================================
PHASE 17 — ORDER PLACEMENT SECURITY
========================================================

Critical:

Order placement must re-check access
on the server.

Do not trust:

- Frontend service visibility
- Old quotations
- Browser access flags
- Submitted customer group IDs
- Submitted policy IDs
- Client-side price values

Before charging:

1. Authenticate customer.
2. Resolve tenant/customer.
3. Resolve authoritative service.
4. Verify global availability.
5. Resolve current access policies.
6. Reject forbidden service.
7. Calculate effective Slice 6A price.
8. Validate quotation freshness.
9. Validate wallet balance.
10. Atomically create order and debit wallet.
11. Preserve ledger and activity behavior.

A denied order must not create:

- Service order
- Wallet debit
- Ledger transaction
- Financial Activity event

Do not alter existing successful
order-processing behavior.

========================================================
PHASE 18 — CONCURRENCY / TOCTOU
========================================================

Handle the race between:

- Reseller changing access policy
- Customer placing an order

A request must not pass authorization
using a stale policy and then commit
after the policy was revoked.

Define a coherent transaction boundary.

Recommended:

Use the same PostgreSQL transaction
for final authorization and order charge.

Use appropriate row locking,
policy versioning or serialization.

Do not rely on an authorization check
performed only before the transaction.

Ensure changes to group membership,
group activation, service availability,
category availability and policies
cannot produce inconsistent access.

Avoid unnecessary global locks.

Preserve existing wallet/order locking
and idempotency.

========================================================
PHASE 19 — EXISTING ORDERS
========================================================

Changing access permissions affects
future orders only.

Do not:

- Delete old orders
- Rewrite old order prices
- Automatically refund historical orders
- Change order statuses
- Cancel existing processing orders
- Rewrite ledger entries

A previously accepted order remains
historically valid.

Existing order history remains visible
to the customer even when the service
is no longer available for new orders.
