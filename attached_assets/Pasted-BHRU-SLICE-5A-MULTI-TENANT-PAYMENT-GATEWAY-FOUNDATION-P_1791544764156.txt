==================================================
1. CORE ARCHITECTURE
==================================================

Payment Gateway definitions are controlled
exclusively by the Platform Admin.

Resellers cannot create or upload gateway plugins.

Resellers can only configure and activate gateways
made available by the Platform Admin.

Customers can only use gateways activated
by their own reseller.

Strict tenant isolation is mandatory.

==================================================
2. PLATFORM ADMIN — PAYMENT GATEWAYS
==================================================

Add Payment Gateways management to the existing
private Platform Admin interface.

Preserve the existing private admin URL,
authentication and authorization.

Platform Admin can:

- View installed gateway definitions
- Enable/disable a gateway globally
- Control availability to resellers
- View gateway integration status
- View supported currencies
- View supported payment methods
- View required configuration fields
- View integration version
- View whether automatic confirmation is supported

IMPORTANT:

Gateway implementations must be registered
in trusted application code.

Do not allow arbitrary executable code,
custom webhook scripts or uploaded plugins.

Do not create a generic API endpoint that allows
a reseller to define an arbitrary payment provider.

==================================================

Create a typed payment gateway registry.

Each gateway definition should describe:

display_name

Do not invent API endpoints for payment providers.

==================================================
4. RESELLER — PAYMENT GATEWAYS
==================================================

Add a Payment Gateways section to the
existing reseller dashboard.

Reseller can:

- View available gateway definitions
- Activate/deactivate supported gateways
- Enter required credentials
- Configure supported payment currencies
- Configure minimum/maximum funding amounts
- Configure customer-visible instructions
- Configure permitted fees where supported
- View connection/validation status

Only show activation controls for gateways
with implemented integrations.

Unavailable gateways should be clearly marked
Coming Soon or Not Integrated.

==================================================
5. CREDENTIAL SECURITY
==================================================

Gateway credentials belong to each reseller.

Never expose secrets in API responses.

Encrypt sensitive credentials at rest using
authenticated encryption and a server-side key.

Do not store encryption keys in the database.

Do not include secrets in:
- activity logs
- HTTP logs
- error messages
- browser responses
- frontend bundles

Support safe credential replacement.

Never display the original secret after saving.

==================================================

Display only gateways that are:

- globally enabled

- compatible with the customer's funding currency

Show:

No fake payment confirmation.

No automatic wallet credit without verified

==================================================
7. CURRENCY RULES
==================================================

Customer Account Currency is immutable.

Payment Currency may differ from Account Currency.

Example:

Account Currency: DZD
Payment Currency: USD

The system must calculate and freeze:

- requested wallet credit in DZD
- payment amount in USD
- exchange rate
- applicable fees
- expected provider amount

Use the existing reseller-approved FX model.

Never silently convert existing wallet balances.

Use exact decimal/integer-minor-unit arithmetic.

Never use JavaScript floating-point arithmetic
for financial settlement.

==================================================
9. PAYMENT TRANSACTIONS
==================================================

Create a separate payment transaction model.

Store:

tenant
customer
funding request
gateway

payment status
payment amount/currency

timestamps

Never store card numbers or CVV.

Provider transaction references must be
uniquely constrained in the appropriate
gateway/tenant scope.

==================================================
10. AUTOMATIC WALLET CREDIT
==================================================

Design a central payment settlement service.

Only a verified successful payment event
may trigger automatic wallet credit.

Settlement must atomically:

1. Verify funding request state
2. Verify expected payment amount/currency
3. Verify provider transaction identity
4. Lock relevant funding/wallet records
5. Mark payment settled
6. Credit customer wallet
7. Insert immutable ledger entry
8. Record client Activity event

All inside the appropriate database transaction.

Retries must never credit twice.

Never trust customer browser redirects
as proof of payment.

==================================================
11. WEBHOOK SECURITY
==================================================

Prepare a gateway-specific webhook architecture.

Every implemented provider adapter must define
its own verified callback/authentication mechanism.

Require:

- signature/authentication verification
- provider transaction validation
- tenant/gateway resolution
- replay protection
- idempotent processing
- amount/currency verification
- safe error handling

Do not implement a universal
"payment_success=true" endpoint.

Do not invent webhook signature formats.
